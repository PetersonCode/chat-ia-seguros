# 15 · Cierre, pendientes y evidencia

## Cierre de casos y acciones administrativas

Un caso no se puede cerrar mientras tenga acciones en `pendiente` (falta
aprobación) o `aprobada` (falta gestión externa). El backend devuelve un error
de estado con el número de acciones en cada condición y conserva el caso
abierto. El detalle de conversación muestra cada acción, su estado y un enlace
al filtro correspondiente del panel de acciones; el botón de cierre queda
deshabilitado mientras haya trabajo pendiente. Una acción `aprobada` no se
presenta como ejecutada, pago devuelto ni modificación aplicada.

La versión corregida incorpora **Registrar gestión completada** en Acciones. Solo un aprobador activo puede finalizar una gestión externa aprobada, indicando referencia y motivo. La finalización conserva responsable y fecha propios, sin sobrescribir la aprobación original. Una vez resueltos los demás pendientes, el caso puede cerrarse. El sistema registra la evidencia administrativa: no ejecuta transferencias ni cambios en sistemas de aseguradoras.

## Guion de recorrido del equipo (10–15 minutos)

Usar una base PostgreSQL de pruebas o una base local nueva con datos ficticios.
No ejecutar `00_drop_all.sql` sobre datos que se quieran conservar. Tener dos
sesiones de navegador, una con un funcionario aprobador y otra con un operador.

| Tiempo | Acción y evidencia que observar |
|---|---|
| 0–2 min | Iniciar sesión con ambos roles. Comprobar acceso al panel; verificar que el operador no puede aprobar acciones y que el aprobador sí. |
| 2–4 min | Desde la ficha de una póliza, registrar un cobro con referencia e importe completo. Repetir la misma referencia y mismos datos: debe volver el cobro existente sin descontar otra cuota. Reutilizar la referencia con un importe distinto: debe rechazarse. |
| 4–6 min | En un cliente ficticio con varias pólizas, abrir una baja sin póliza, elegir una póliza real, revisar el número seleccionado y aprobar. Confirmar que solo esa póliza cambia de estado. |
| 6–7 min | Enviar una frase de urgencia como “Tuve un choque”. Comprobar prioridad urgente en la bandeja, derivación humana y que no depende del resultado del LLM. |
| 7–8 min | Con el chat en modo bot, dejar un mensaje pendiente y tomar el chat desde la sesión humana. Confirmar que no sale la respuesta automática común; enviar una imagen y comprobar que el bot no contesta durante la atención humana. |
| 8–10 min | Registrar una denuncia de siniestro desde el panel, avanzar por estados permitidos y adjuntar una imagen admitida. Verificar que la descarga requiere sesión y que el registro queda vinculado al expediente correcto. |
| 10–11 min | Aplicar un período en reportes y exportar CSV. Contrastar consultas, estados, urgencias y cobros contra una muestra conocida en la base. |
| 11–13 min | Intentar cerrar un caso con una gestión externa aprobada: debe bloquearse. Desde Acciones registrar su finalización con referencia y motivo; verificar historial y completar el cierre. |
| 13–15 min | Registrar fecha, commit/revisión probada, base y resultado de cada paso en la tabla de evidencia siguiente. Anotar fallos o pasos no completados; no marcar credenciales reales ni datos personales en la evidencia. |

## PostgreSQL implementado y SQL Server propuesto

El repositorio se implementa y prueba contra PostgreSQL; no hay conmutador de
motor ni soporte para SQL Server. Los scripts y consultas incluyen `jsonb`,
índices parciales, expresiones regulares, triggers PL/pgSQL y reclamos con
`SELECT FOR UPDATE SKIP LOCKED`. SQL Server tiene dialecto, tipos, triggers y
semántica de bloqueo distintos. Una propuesta de migración necesita diseño y
pruebas específicas para esquema, consultas, restricciones e idempotencia; no
se puede resolver cambiando una variable de configuración. Esta entrega no
cambia el motor, no hace push y no despliega.
